## What the PR does

`DialogPeriodDateEdit.vue` (the dialog used to move a period or change its start/end in the camp admin) now overrides `onSuccess` to reload the three collections whose dates are derived from the period start:

```js
onSuccess(response) {
  this.api.reload(this.period.scheduleEntries())
  this.api.reload(this.period.days())
  this.api.reload(this.period.dayResponsibles())
  return DialogBase.methods.onSuccess.call(this, response)
}
```

It then delegates to `DialogBase.methods.onSuccess` so the `success` event, `successHandler` and dialog closing keep working.

## Root cause (verified)

- The API does **not** store absolute dates for schedule entries and days. It stores offsets (`startOffset`, `dayOffset`) and computes `start`/`end` from the period start (`api/src/Entity/ScheduleEntry.php::getStart()`, `api/src/Entity/Day.php::getStart()`).
- When a period is moved or its start/end changes, `api/src/State/PeriodPersistProcessor.php` shifts entries/days (or adds/removes days) **without those resources being written** — only the period is PATCHed.
- The frontend HAL cache (`hal-json-vuex`) keeps the old computed dates. `CampProgram.vue` loads `period.scheduleEntries()`, `period.days()`, `period.dayResponsibles()` via `_meta.load`, which resolves from the cache **without a network request**.
- Result: the Picasso renders the new date range with entries on the old dates → empty Picasso. Day responsibles disappear because `DayResponsibles.vue` finds the day by comparing `day.start` with the calendar date.
- `DialogPeriodDateEdit` is the **only** place in the frontend that PATCHes period start/end, so fixing it at the mutation point covers all paths.

## Code review findings

### Blocking
- None.

### Non-blocking (no change needed)

1. **`changeEnd` mode reloads `scheduleEntries` unnecessarily** — entry dates are computed from period *start* offsets, so changing only the end doesn't move them. Harmless (one extra GET), keeps the code mode-agnostic. Right tradeoff.
2. **Fire-and-forget reloads** — `api.reload()` promises are neither awaited nor caught; a network failure would leave an unhandled rejection and stale UI until the next reload. This is exactly the established codebase pattern (`DialogActivityEdit.vue`, `CategoryProperties.vue`, `Camps.vue`, `CollaboratorCreate.vue`), so it's consistent.
3. **`this.period.scheduleEntries()` returning `undefined`** would throw synchronously and skip the base `onSuccess`. Not realistic — the `period` prop always comes from the API with these relations, and the codebase makes the same unguarded assumption elsewhere.
4. **Test mock URIs differ from real API templates** (e.g. `/days?period=/periods/1` vs real `/periods/{periodId}/days`) — cosmetic only; assertions check object identity, never URI strings.

### Test quality

- `it.each` covers all three modes (`move`, `changeStart`, `changeEnd`).
- Failure path covered: PATCH rejects → no reload, dialog stays open.
- Dialog-close test proves the base `onSuccess` delegation is preserved (`showDialog === false`, `success` emitted once).
- Mocks are faithful to how the component uses `api` (`get` returns `{ _meta: { load: Promise.resolve(...) } }` matching `DialogBase.loadEntityData`; `patch`/`reload` match `update()` usage).
- Follows repo spec conventions (matches `CommentComposer.spec.js` style).

### Coverage gaps (minor, none blocking)

- No assertion that `successHandler` prop is still invoked (base behavior, out of scope).
- No e2e test for the actual scenario (admin → move period → back to Picasso). The e2e `httpCache` specs verify server-side cache invalidation via direct API calls, not the frontend HAL cache. A UI-level e2e would be the remaining coverage gap; the PR author verified the scenario manually.
